12. CONNECTION NAMING CONVENTIONS
================================================================================

NAMING SCHEME FOR EXPANDED BLUEPRINTS:

Parent Level (before expansion):
  device_reference: lamp
  port_name: vin
  connection_string: lamp.vin

After Expansion (internal blueprint devices):
  device_name: lamp:internal_device
  connection_string: lamp:internal_device.port

Bridge Nodes (after top-level rewrite):
  device_name: lamp:vin (where "vin" is the exposed port name)
  external_port: lamp:vin.ext (parent-facing)
  internal_port: lamp:vin.port (child-facing)
  connection_string (parent): lamp:vin.ext (rewritten from lamp.vin)
  connection_string (internal): lamp:vin.port (for connections within expanded blueprint)

COLON SEMANTICS:
  - Single colon (:) separates blueprint instance name from internal element
  - E.g., battery_module:bat is device "bat" inside blueprint instance "battery_module"
  - E.g., lamp:vin is bridge node "vin" inside blueprint instance "lamp"

DOT SEMANTICS:
  - Dot (.) separates device from port
  - Double colons and dots (e.g., lamp:vin.ext) indicate blueprint:bridge_element.side

13. DOMAIN CONSTRAINT
================================================================================

ALL BLUEPRINT BRIDGE NODES (BlueprintInput and BlueprintOutput) are in:
  Domain::Electrical (value = 0b00001)

This is defined in:
  - blueprint_input.h, line 12: static constexpr Domain domain = Domain::Electrical;
  - blueprint_output.h, line 12: static constexpr Domain domain = Domain::Electrical;

Port Registry Encoding:
  - Domain bitmask value 1 = Electrical domain
  - Lines 645-648 (BlueprintInput): both ports are domain 1
  - Lines 659-662 (BlueprintOutput): both ports are domain 1

CONSEQUENCE: Bridge nodes cannot be used to expose ports from other domains
             (Logical, Hydraulic, Mechanical, Thermal). If cross-domain
             exposure is needed, separate bridge mechanisms or multi-domain
             components would be required.
